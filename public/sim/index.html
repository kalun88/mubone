● OSC sensor

sample instrument

accessory — 8 analogue channels

no accessory
pad volts value type destination input min max curve calibrate invert

pad — matches the silkscreen on the accessory board. − and + are ground and the 3.0 V rail; pads 1–8 are the inputs.
type — pot and slider are continuous and can drive any value destination. button is on/off and can only target bang or hold actions. Changing the type re-filters the destination list.
calibrate — click, sweep the control through its full travel, click again. Pots rarely reach the rails, so this maps whatever range the hardware actually produces onto 0–1. Buttons don't need it. A sweep narrower than 0.05 V is rejected as a mis-click rather than saved.
min / max — where the two ends of the pot's travel land, in the destination's own units. Leave them at the full span for the whole range, or narrow them to spend the entire throw on the part you actually play — −600 ¢ to +600 ¢ turns a two-octave pitch control into a usable semitone one. Swapping them so min is above max reverses the throw.
curve — response exponent. 1 is linear; above 1 packs more travel into the bottom of the range (fine control down low, coarse up top), below 1 does the reverse. Double-click to reset min, max and curve together.
bangs vs holds — a bang action (undo, sweep) fires on press only. A hold action (erase brush) is on while held and releases when you let go — including if the accessory is unplugged mid-hold, so nothing sticks on. Continuous channels freeze at their last value on unplug rather than dropping to zero.

x-imu3 led mapping

feedback off
on function colour pattern count rate test

states vs events — a state is held for as long as its condition is true, and exactly one is active at a time. An event fires once and then the current state resumes. An event interrupts a running state pattern rather than layering over it.
patterns — solid is a held colour. slow (1.5 Hz) and fast (5 Hz) are on/off blinks. pulse breathes through eight brightness steps per cycle. flash is the crisp 90 ms blip used for events. For events, count is how many times the pattern repeats.
slow ⇄ timbre and fast ⇄ timbre alternate the row's colour with the live scan timbre instead of with black, so the LED carries two facts at once — e.g. muted on white/fast tells you the output is dead and what you'd be hearing if it weren't. Costs no more than plain slow/fast: same two edges per cycle, the off-phase is just a different colour. Falls back to black when nothing is under the cursor rather than holding a stale colour. Not offered on scan, where it would interleave timbre with itself.
timbre is offered on the scan row only — it's a colour source rather than a pattern, and it can only mean something while the cursor is granulating. It paints the LED with the same colour the visualiser gives the particles the cursor would fire from right now — the scheduler's own candidate pool, weighted so material at the centre of the radius dominates. Bass regions blue, bright regions orange, noisy material desaturated. Reading the pool rather than the grains that happen to be sounding keeps the response independent of dur and period: the colour tracks the cursor, not the grain clock. When nothing is in radius the state falls back to idle, so silence reads as whatever idle is set to (black by default). The readout up top shows the live colour and how many particles are in range, or names what's missing. Hue matches the screen exactly; saturation is stretched and lightness lowered because the emitter washes the viz's pale end out to white. When the cursor isn't firing, the last colour is held rather than going dark.
rate — messages per second sent to the sensor while the row is running (plus burst length, for events). The x-IMU3 has no device-side blink with colour or rate control, so every on and off edge is a message from here. On WiFi those share the radio with the inbound data frames: if raw readings ever start looking glitchy, this column is where to look first. Only the sensor holding the cursor role ever animates — the others get a single solid idle write.
disabling a state falls back to idle rather than to the firmware's own colour. Disabling idle itself releases the override entirely and hands the LED back to the firmware.
live readout — the state row driving the LED right now carries a ▸ marker, and events flash their row as they fire. The defaults reproduce the palette that used to be hardcoded, so this is how you confirm the table is what's actually driving the sensor. If an event doesn't fire, the readout up top says why (row off, no cursor x-imu3, feedback off).

keys / midi / osc

function default key override key learn midi midi learn osc data

data column — describes what the OSC endpoint accepts. bang = zero-argument message (just the address, no value). int n|m = integer with listed options. int a–b / float a–b u = numeric range in unit u.
how bangs are triggered — OSC: send the address with no args (any args are accepted but ignored). MIDI: bang-type actions mapped to a CC fire once on press (value > 0); the matching value-0 release is dropped, so Softwave-style "trigger" mode (sends 127 then 0) produces exactly one action per tap. Note-on/off works the same way — note-on fires, note-off is ignored for bangs.

driving this window from Max — simplest: [udpsend 127.0.0.1 7500] and send messages exactly as the osc column shows, e.g. /preset 3 or /trace 1. This window is solo.
multi-station via max/bridge.js — run [node.script bridge.js] in the patch, send setmode electron once, then every message routes to the selected station (a=7500 b=7510 c=7520): setstation b = following messages go to station b · setstation all = go to every station · to b /trace 1 = one-shot to b without changing the selection · setstations a b c = define what "all" means. Anything else passes through to the station unchanged.
