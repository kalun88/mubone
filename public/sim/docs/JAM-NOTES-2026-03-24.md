## Design Principle: No Haptic Feedback — Vision Carries All Spatial Confidence

Unlike every acoustic instrument, mubone has no physical stops, frets, valve detents, string tension, or slide positions — nothing that tells the performer's body where it is without looking. A trombonist feels slide positions. A pianist feels key edges. Mubone has zero haptic confirmation of spatial state.

This means **all orientation confidence must come through visual feedback.** Every visual reference marker in the system is load-bearing — it's compensating for the absence of an entire sensory channel. This applies to: tare origin markers, state indicators, the flat map projection, cursor mode visuals, drift detection cues. These are not cosmetic — they are the instrument's equivalent of frets and valve stops.

This principle should inform every UI/viz decision: when in doubt, make state visible.

## 3. Sensor Drift & x-IMU3 Configuration

**Observation:** The x-IMU3 was drifting counterclockwise consistently during the session.

### Current x-IMU3 Settings (confirmed from GUI)

| Setting | Current value | Default | Notes |
|---------|--------------|---------|-------|
| AHRS ignore magnetometer | **enabled** | false | Already ignoring mag — drift is NOT a magnetometer problem |
| AHRS acceleration rejection | enabled | true | Correct — rejects accel during dynamic motion |
| AHRS gain | 0.5 | 0.5 | Controls how aggressively accel corrects gyro (pitch/roll only) |
| Gyroscope offset correction | enabled | true | Estimates and removes gyro bias at rest |
| UDP low latency | **disabled** | — | **Should enable for real-time performance** |
| Message rate | 100 Hz | 50 Hz (divisor 8) | Good for real-time. Could try 200 Hz (divisor 2) |
| Magnetometer messages | disabled | enabled (divisor 1) | Correct since mag is ignored in AHRS |
| Binary mode | disabled | true | ASCII is fine but binary is more efficient |

### Key Finding: Drift Is Pure Gyro (Not Magnetometer)

Since `ahrs_ignore_magnetometer` is already enabled, the counterclockwise yaw drift is **not** caused by magnetic interference. It's inherent gyro drift. With mag ignored, the AHRS has no absolute yaw reference — only the gravity vector anchors pitch and roll via the accelerometer. Yaw will always wander slowly because there's nothing to correct it. The gyroscope offset correction helps at rest but can't fully compensate during continuous playing.

**This means the drift is expected behavior with current settings.** The tradeoff is: magnetometer on = yaw is anchored but susceptible to magnetic interference in performance spaces; magnetometer off = no magnetic interference but yaw drifts. For improv with periodic re-taring, mag off is probably still the better choice.

### Recommended Setting Changes

- [ ] **Enable UDP low latency** — no reason not to for real-time performance. Reduces transport delay.
- [ ] **Try AHRS gain 0.7–1.0** — higher gain means more aggressive accelerometer correction of pitch/roll. Won't help yaw drift (nothing will without mag) but keeps pitch/roll tighter. With acceleration rejection enabled, motion artifacts are already handled, so higher gain is relatively safe.
- [ ] **Consider enabling binary mode** — more compact messages, slightly lower parsing overhead. Low priority but free improvement.
- [ ] Document the drift rate roughly (degrees per minute) so we can track whether gain changes help.

### CRITICAL: Max/OSC Initialization — Don't Accidentally Change Settings

**Warning:** The x-IMU3 accepts setting commands over serial and Wi-Fi (JSON key-value writes, see manual section 8.1.2). When initializing the serial or Wi-Fi stream from Max, make sure the Max patch is **not** inadvertently sending write-setting commands that could change AHRS settings (e.g., re-enabling magnetometer, changing gain, altering message rates). Audit the Max bridge initialization sequence for any outgoing setting messages.

**Opportunity — Send Settings on Init:** The x-IMU3 command protocol supports reading and writing any device setting at any time. The Max patch (or mubone's OSC bridge) could send a settings confirmation sequence on connection to guarantee the correct configuration regardless of what the GUI was last set to. For example, on init:

```
Write ahrs_ignore_magnetometer = true
Write ahrs_gain = [desired value]
Write ahrs_acceleration_rejection_enabled = true
Write gyroscope_offset_correction_enabled = true
Write udp_low_latency = true
Apply settings
```

This way the performer doesn't need to open the x-IMU3 GUI before each session — the app enforces the right config.

**Heading Command (Tare via Software):** The x-IMU3 has a "heading command" (manual section 8.1.19) that resets the yaw reference — this is effectively a software-triggered tare/zero for heading. This could be sent from mubone when the performer presses the tare button, so the tare happens at both the mubone level AND the sensor level simultaneously.

**Action items:**

- [ ] Audit the Max patch initialization for any x-IMU3 setting writes that could conflict with desired config.
- [ ] Implement a settings confirmation sequence on connection (send desired settings + apply command).
- [ ] Investigate using the heading command as part of the mubone tare flow — tare both sensor and viz origin together.
- [ ] Test the "default" command (8.1.3) to understand what it resets — make sure it doesn't get sent accidentally.

### x-IMU3 Settings Reference — What Every Lever Does

Complete reference for the x-IMU3 GUI settings relevant to mubone performance. Source: x-IMU3 User Manual v1.11.

**AHRS Settings:**

| Setting | JSON key | Type | Default | What it does |
|---------|----------|------|---------|-------------|
| AHRS gain | `ahrs_gain` | number | 0.5 | Controls how aggressively the accelerometer (gravity) corrects gyro integration. Higher = less pitch/roll drift but more sensitive to motion artifacts. Only affects pitch and roll — has NO effect on yaw because gravity doesn't provide a yaw reference. Range is 0 to ~10+; typical useful range 0.1–2.0. |
| Ignore magnetometer | `ahrs_ignore_magnetometer` | bool | false | When true, the AHRS uses only gyro + accelerometer (no magnetic heading). Eliminates magnetic interference but removes the only absolute yaw reference — yaw will drift over time. When false, magnetometer anchors yaw but is susceptible to nearby speakers, laptops, metal. |
| Acceleration rejection | `ahrs_acceleration_rejection_enabled` | bool | true | When enabled, the AHRS detects dynamic acceleration (movement, not just gravity) and temporarily reduces the accelerometer's influence on the orientation estimate. Prevents fast movements from corrupting the pitch/roll estimate. Should always be on for performance use. The GUI viewer shows an **acceleration recovery** flash indicator when this is active. |
| Magnetic rejection | `ahrs_magnetic_rejection_enabled` | bool | true | When enabled, detects magnetic distortion and temporarily reduces magnetometer influence. Only relevant when ignore magnetometer is false. The GUI viewer shows a **magnetic recovery** flash indicator when active. |
| AHRS axes convention | `ahrs_axes_convention` | number | 0 (NWU) | Earth frame convention: 0 = North-West-Up, 1 = East-North-Up, 2 = North-East-Down. Affects how the AHRS reports orientation relative to Earth. |
| AHRS message type | `ahrs_message_type` | number | 0 (Quaternion) | Output format: 0 = Quaternion, 1 = Rotation matrix, 2 = Euler angles, 3 = Linear acceleration, 4 = Earth acceleration. Mubone uses quaternion (0). |

**Sensor Processing:**

| Setting | JSON key | Type | Default | What it does |
|---------|----------|------|---------|-------------|
| Gyroscope offset correction | `gyroscope_offset_correction_enabled` | bool | true | Continuously estimates and removes gyro bias (drift) when the sensor is stationary. Essential for reducing drift — should always be on. Works best when there are periodic moments of stillness. |
| Axes alignment | `axes_alignment` | number | 0 (+X+Y+Z) | Remaps the physical sensor axes to match your mounting orientation. 24 possible alignments. Could handle rotation at the sensor level instead of in mubone's axis map software. |

**Network / Transport:**

| Setting | JSON key | Type | Default | What it does |
|---------|----------|------|---------|-------------|
| UDP low latency | `udp_low_latency` | bool | — | Reduces transport delay for UDP messages. Should be enabled for real-time performance — no downside. |
| Binary mode | `binary_mode_enabled` | bool | true | Binary messages are more compact and faster to parse than ASCII. Lower latency, less bandwidth. Currently disabled (using ASCII) — consider enabling. |

**Message Rates:**

The x-IMU3 internal sample rate is fixed at 400 Hz for inertial/AHRS data. Message rates are configured via divisors (400 / divisor = messages per second).

| Setting | JSON key | Default divisor | Default rate | What it does |
|---------|----------|----------------|-------------|-------------|
| Inertial message rate | `inertial_message_rate_divisor` | 8 | 50 Hz | Raw gyro + accelerometer data. Used for gesture/inertial analysis. |
| AHRS message rate | `ahrs_message_rate_divisor` | 8 | 50 Hz | Orientation output (quaternion/euler). This is the cursor data. Currently set to divisor 4 (100 Hz). |
| Magnetometer message rate | `magnetometer_message_rate_divisor` | 1 | 20 Hz | Raw magnetometer data. Currently disabled (divisor 0) — correct since mag is ignored. |

Note: if the message rate is lower than the sample rate, samples are **averaged** (section 9.3 of manual). So at 100 Hz (divisor 4), each message is the average of the 4 most recent 400 Hz samples — this smooths the output slightly.

**GUI Viewer Flash Indicators (diagnostic):**

| Indicator | What it means |
|-----------|--------------|
| **Angular rate recovery** | Gyro is recovering from saturation (movement exceeded ±2000°/s range). If this flashes during normal playing, your movements are hitting the gyro limit — sensor accuracy is temporarily degraded. |
| **Acceleration recovery** | AHRS is rejecting accelerometer input due to detected dynamic motion. This is the acceleration rejection system working correctly. Expected to flash during movement, stop when still. Normal. |
| **Magnetic recovery** | AHRS is rejecting magnetometer input due to detected magnetic distortion. Only relevant when magnetometer is not ignored. If this flashes with mag ignored, something unexpected is happening. |

**Commands (can be sent from Max/mubone):**

| Command | Manual section | What it does |
|---------|--------------|-------------|
| Heading command | 8.1.19 | Resets yaw reference (heading zero). **Yaw only** — does not affect pitch or roll. Pitch/roll are always referenced to gravity. |
| Initialise AHRS | 8.1.18 | Reinitializes the AHRS algorithm. Useful if orientation is stuck or corrupted. |
| Read/Write settings | 8.1.1 / 8.1.2 | Read or change any device setting via JSON key-value pairs. |
| Apply | 8.1.4 | Applies written settings (must send after write commands). |
| Save | 8.1.5 | Saves current settings to flash (persist across power cycles). |
| Default | 8.1.3 | Resets ALL settings to factory defaults. **Dangerous — do not send accidentally.** |

### Mubone Tare vs. x-IMU3 Heading Command — What Each Does

**Mubone tare (software, in `sensor-registry.js`):** Captures the current raw quaternion as `tareQuat`, then computes `tareQuat⁻¹ × currentQuat` for all subsequent readings. This is a **full 3D tare — all three axes (yaw, pitch, and roll)**. Whatever orientation the sensor is in at tare time becomes the new (0,0,0). This means you CAN tare while pointing below the horizon, and that downward angle becomes your zero. The math is correct for arbitrary orientations.

**x-IMU3 heading command (hardware, section 8.1.19):** Resets the AHRS yaw reference only. **Pitch and roll are NOT affected** — they are always referenced to gravity (the accelerometer defines "level"). This command tells the sensor "wherever I'm pointing in yaw right now is heading zero." It does not change the pitch/roll reference.

**What this means in practice:**

- Mubone tare handles the full 3D zero — including pointing below the horizon. If this isn't working in your tests, there may be a bug in the axis map chain (the path from tared quaternion through `applyAxisMapQuat` into the renderer).
- The heading command is useful *in addition to* mubone tare — it resets the sensor's internal yaw accumulation, which could slow drift between tares. Think of it as a drift-reduction tool, not a replacement for mubone tare.
- **Recommended tare flow:** When the performer presses tare in mubone: (1) send heading command to x-IMU3 (resets sensor yaw), (2) capture `tareQuat` in mubone (resets all three axes in software), (3) flash the tare origin marker on the viz. This gives the best of both — hardware yaw reset + software full-3D zero + visual confirmation.

**If below-horizon tare is not working:** The quaternion tare math (`qMulQ([-tx, -ty, -tz, tw], quat)`) is correct for arbitrary orientations. If it's not behaving as expected, the issue is likely downstream — possibly the axis remap (`applyAxisMapQuat`) or the Euler decomposition is flattening the pitch component. This is worth investigating as a bug.

**Action items:**

- [ ] Test below-horizon tare systematically: tare while pointing ~30° down, verify that the viz shows center, move back to level and confirm cursor shows ~30° up from center.
- [ ] If below-horizon tare fails, trace the quaternion path: `slotTare` → `applyTare` → `applyAxisMapQuat` → renderer to find where pitch information is being lost.
- [ ] Implement combined tare flow: heading command to sensor + quaternion tare in software + viz flash, all from one button.
- [ ] Use heading command on each tare to reset yaw drift accumulation at the hardware level.

### 3b. Tare Origin Marker & Drift Confidence

**Need:** High confidence in sensor accuracy during performance. Currently there's no way to visually confirm whether the sensor has drifted from its tare position. Since the instrument has no haptic feedback (see design principle above), this confidence has to come entirely from visual references.

**Idea — visible tare origin on the viz:** Show a persistent marker (crosshair, ring, or axis indicator) at the (0,0) tare position on the sphere/map. This acts as a "north star" — the performer can glance at it and know where center is. If they're pointing straight ahead physically but the cursor isn't near the tare marker, they can see the drift and re-tare. Eyes become the drift detector.

**Tare zone (not just a point):** Rather than a single-pixel origin, show a subtle circle or region around the tare point. This gives a "neighborhood" of center rather than demanding pixel-precision alignment. Ties into the painting area / boundary concept from section 4b.

**Flash on re-tare:** When the performer re-tares, briefly flash/pulse the tare marker to give visual confirmation that the origin has been reset. Important because the tare action is intentional but the effect is invisible without this — you press a button and nothing visually confirms it worked.

**Precedent:** This is standard practice in VR/spatial interfaces — most VR systems show a forward marker or play-space boundary so the user knows where center is. Head trackers show a calibrated-center reticle. Same principle applies here.

**Action items:**

- [ ] Add a persistent tare origin marker to the viz (crosshair or ring at the 0,0 tare position).
- [ ] Add a brief flash/pulse animation on the tare marker when re-tare is triggered.
- [ ] Consider a "tare zone" radius rather than a point — subtle circle showing the centered neighborhood.
- [ ] This marker should be visible in both sphere mode and the future flat map mode.

**Comment:** This is low-effort, high-confidence. A few lines in the renderer to draw a fixed marker at the tare origin. The flash on re-tare is a small animation trigger. Together they give the performer a constant spatial anchor — which, given the no-haptic-feedback design constraint, is essential infrastructure rather than a nice-to-have.

## 4. Sensor Mounting Position — Why Extended Mounting Feels "Less"

**Observation:** When the sensor is mounted at an extended position (wrist, trombone bell), the cursor seems to move less than expected given the physical movement.

**Explanation:** The IMU measures *orientation* (rotation), not *position*. It doesn't know where it is in space — only which way it's pointing. This creates an important asymmetry:

- **Sensor close to a rotation axis** (e.g., on your chest/torso): when you turn your body, the sensor rotates the full amount. 30° body turn = 30° sensor rotation = 30° cursor movement.

- **Sensor at the end of a limb** (wrist, bell): your natural movements at the extremities tend to be *translational* — your hand sweeps through a large arc of space, but the sensor's own orientation may barely change. Think of holding a tray level while moving your arm around — the tray travels far but stays flat. The IMU reads "almost no rotation" even though your hand moved a lot.

The mismatch is perceptual: you *feel* like you're making a big movement (because your hand traveled far through space), but the sensor only cares about angular change at its mounting point. Small wrist flicks actually register more than large arm sweeps.

**Action items:**

- [ ] Experiment with a sensitivity/gain multiplier for cursor mapping — so smaller rotations at extended mounting positions can still cover the full sphere. This could be a per-setup calibration value.
- [ ] Test mounting the sensor closer to a joint (forearm rather than wrist/bell) to see if the feel improves.
- [ ] Consider whether the gain should be user-adjustable in the sensor panel, since optimal sensitivity depends on mounting position and personal movement style.
- [ ] For improv specifically: since movements will be small/subtle, a higher sensitivity setting is probably needed regardless of mounting position.

**Comment:** This is a fundamental characteristic of orientation-based control. A gain/sensitivity control in the sensor panel would be the simplest fix and would make the instrument adaptable to different mounting positions without code changes. Could be as simple as a multiplier on the Euler deltas before they hit the cursor position.

### 4b. Flat Map Projection & Painting Area (new idea from session)

**Observation:** The 3D sphere visualization is a great simulation, but in "desktop mode" (not performing in real space), it limits your view to whatever part of the sphere you're currently facing. The view area changes and moves, which can be disorienting. Felt like there wasn't enough space to "paint."

**Idea — flat map projection:** An alternative viz mode that shows the entire sphere unfolded as a flat map (like a Mercator or equirectangular world map projection). This would let the performer see *everything* at once — all seeds, all recorded material, the full painting surface — without rotating the view.

**Idea — definable painting area / boundary:** In a flat projection, you could define a maximum physical movement boundary — the area your body/instrument actually covers. For example, draw a big circle with the trombone slide to define the painting region. The sensor's range maps onto this region, giving you full coverage of your working area with natural movements.

**Extended idea — boundary as a mode gate:** The area *outside* the defined boundary could trigger a different behavior — a mode switch, a parameter zone, a "no-paint" region. So the boundary isn't just a limit, it's a performance interface. You move inside to paint, move outside to do something else.

**Calibration gesture:** To set the boundary, you'd do a calibration gesture — extend the trombone slide fully and trace the outer edge of your comfortable range. The system captures that as your working envelope. Same concept with a hand-mounted sensor.

**Action items:**

- [ ] Prototype an equirectangular flat map projection as an alternative viz mode (toggle between sphere and flat map).
- [ ] In flat map mode, implement a "define painting area" calibration: performer traces their physical movement range, system maps that onto the full canvas.
- [ ] Explore what "outside the boundary" could mean — mode switch, parameter zone, sweep trigger, etc.
- [ ] Consider resolution/zoom within the painting area — smaller physical range could still map to fine-grained placement if the gain is right.

**Comment:** This is a significant idea. The flat map solves two problems at once: the disorienting moving viewport of the 3D sphere, and the "not enough space" feeling from limited sensor range. It's essentially a resolution/mapping problem — you want your comfortable physical range to cover the entire sonic canvas. The boundary concept adds an extra dimension of control, turning the edge of your movement range into an interface element. For improv especially, seeing everything at once is a huge advantage over rotating a virtual globe. This should be high priority for the desktop/improv workflow.
